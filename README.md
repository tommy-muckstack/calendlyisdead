# CalendlyIsDead
Free, open-source scheduling (Apache-2.0). Next.js + Neon Postgres + Drizzle + Auth.js, deployed on Vercel.

CalendlyIsDead is an independent open-source project, not affiliated with or endorsed by Calendly, LLC.
No Calendly assets, CSS or code; no cal.com (AGPL) code may be copied in. See docs/PLAN.md.

## Run it locally (no keys needed)
```
npm install
npm run dev        # http://localhost:3000, embedded Postgres (PGlite) in .data/, seeded demo host
```
- Demo booking page: http://localhost:3000/demo/30min
- Host dashboard: /login, then "Use the demo account" (dev only, or `DEMO_MODE=1`)
- Booking emails print to the server log (and `.data/outbox/`) unless `RESEND_API_KEY` is set.

Env (all optional in dev): `DATABASE_URL` (Postgres/Neon), `AUTH_SECRET` (signs the demo cookie and encrypts stored calendar tokens), `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET` (Google *calendar* connect only), `AUTH_MICROSOFT_ID`/`AUTH_MICROSOFT_SECRET`, `RESEND_API_KEY`, `EMAIL_FROM`, `APP_URL`.

## Sign-in (shared across yourappisdead.com)
Firebase Authentication, email/password + Google, shared by every IsDead app (`lib/isdead-auth`, canonical copy in isdead-design/auth).
The browser signs in with the Firebase JS SDK and POSTs the ID token to `/calendlyisdead/api/session`; firebase-admin verifies it,
maps the Firebase uid to `users.firebase_uid` (linking an existing row by *verified* email), and sets an httpOnly `isdead_session`
session cookie with `Path=/`, so /superhumanisdead and /wisprflowisdead see the same sign-in. Sign out clears it and revokes refresh tokens.

Env: `NEXT_PUBLIC_FIREBASE_API_KEY`, `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID`, `NEXT_PUBLIC_FIREBASE_APP_ID`,
`NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID`, `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET`, `FIREBASE_SERVICE_ACCOUNT_JSON` (whole JSON key), optional `ISDEAD_COOKIE_DOMAIN`.
Without them the login page says "Sign-in not configured" (demo button still works with `DEMO_MODE=1`).

## New account setup

A newly created app account starts at `/onboarding`: choose a role, optionally connect a Google or Outlook calendar, then confirm your time zone and weekly hours. The first visit detects the browser time zone; a saved choice survives later sign-ins. Each Continue saves progress. Finish setup atomically creates a default schedule and a linked 30 Minute Meeting; an interrupted request can be retried without duplication. No initial public event exists before completion.

Existing accounts, demo accounts and verified-email links to legacy accounts retain their existing setup. Signed-in login/signup visits return to setup or the app. Calendar authorization returns to unfinished setup, and unavailable provider configuration does not block skipping. Roles are stored preferences; they do not gate features. All features remain free. Exact original choices, copy and layout still need browser comparison.

For isolated onboarding browser scenarios, run `npx playwright test --config playwright.onboarding.config.ts`. The config seeds only synthetic accounts in a fresh `.data/onboarding-e2e/` database, disables external mail and analytics, and avoids deleting the normal demo database/outbox. Fixtures use demo sessions; real Firebase signup and provider consent must be checked separately. These scenarios have been authored but cannot execute in the current browser environment.

## Creating event types

Scheduling → Create → One-on-one, Group, Round robin or Collective opens an unsaved draft. Enter a name and configure the event, then choose **Create** to publish it. **Cancel** leaves no event behind; edited drafts ask before discarding. No event record or public booking link exists until Create succeeds. The link follows the name until you edit it yourself. Generated links receive a suffix when needed; custom links must be available.

Failed requests retain the draft. An unchanged retry checks the same creation request and cannot create a duplicate. If that request already completed and you changed the draft afterward, reload event types to review the saved event. Deleted events cannot be recreated by retrying their old request. Once created, the normal editor provides **Save changes**, host limits and contact automations.

The API persists settings and a minimal creation receipt atomically in the existing database. The older kind-only creation request remains compatible with existing callers. Shared events select accepted members of your workspace, start with you selected, and let you add/remove hosts and choose each host’s availability schedule. The event appears in a separate Shared event types section for its hosts and workspace admins, with a direct link under its creator’s username. It never appears on a public profile. Cohosts can edit, share, embed and duplicate; the creator or workspace admin can delete. Removing yourself loses management access unless you are a workspace owner/admin. Existing meetings remain intact.

Collective meetings reserve every selected host. Round robin assigns one host: maximize availability favors priority then the least recent assignment; equal distribution hides hosts three confirmed meetings ahead. Changing the host set or distribution resets counts. Rescheduling can reassign or retain the original host. Public reschedule links resolve the event creator’s current username and event slug, even when a cohost received the booking. Invitee details prefill only on the booked event’s page. Shared edits use versions to reject stale saves. Reservations recheck event version, memberships, schedules and local conflicts under the same workspace/event/user lock order as edits. Removed or rejoined memberships never silently restore host privileges. If a selected member or schedule becomes unavailable, new booking availability closes until an editor corrects Hosts; existing meetings remain manageable by their actual hosts. Deleting a workspace cannot turn its shared events into personal events.

Multiple host pools, common custom hours, per-host location choices, conferencing organizer selection, explicit editor/viewer permissions, admin meeting management, host-added notification preferences and shared single-use links remain open parity work. Creating a shared event currently requires a workspace configured in People; the exact solo-account setup remains unverified. Common location tiles are available in the draft/editor; automatic provider setup and original editor-pane styling remain pending. See [the parity report](docs/PARITY_REPORT.md).

## Workspace invitations

Settings → Workspace/People creates a free organization, manages members and invites colleagues. New invitations have no expiry. A recipient must sign in with the invited email and explicitly accept. Admins can revoke or resend an invitation; resend replaces all previous links. Removing a member prevents their old accepted links from restoring access.

The existing workflow cron also attempts one reminder for invitations still pending after seven days. The reminder provides a second link while keeping the original valid. Only token hashes are stored. The reminder is claimed transactionally before delivery and is not automatically retried after a provider failure or interrupted attempt; People shows the delivery status and admins can resend explicitly. Without a mail provider, artifacts stay in the local outbox and the UI reports undelivered mail. No provider is enabled by this change.

Older invitations created with the previous seven-day expiry retain that expiry, so migration cannot reactivate expired links. Resend adopts the non-expiring behavior and starts a new seven-day reminder window for those older invitations. Accepted/revoked invitations do not receive reminders. Production cron and provider delivery still require separate verification.

## Profile

Settings → Profile (`/app/profile`) edits your display name, scheduling-page welcome message, photo and account time zone. Use **Save changes** to persist the draft; a failed save retains your edits for retry. Changing the account time zone updates meeting filters and account-limit boundaries without changing existing availability schedules or booking instants.

Photos must be at least 90 × 90 pixels and smaller than 5 MB. JPG, PNG, WebP and GIF uploads become a centered 256px square PNG with metadata removed; animated images become static. Photos are stored in the app database (local PGlite during keyless development), without a separate upload service. Language, country, date/time format and login/security settings are not implemented yet; see [the parity report](docs/PARITY_REPORT.md).

## Contacts

Contacts (`/app/contacts`) supports manual records with name, email, phone, job title, company, LinkedIn URL, time zone, country, city and state. Search by name, email, phone or company; sort by name or last update. Each host has their own records, with one active contact per email address. Use **Save contact** or **Save changes**; failed saves retain the draft, and conflicting edits require an explicit reload.

A contact's history links to that host's meetings whose invitee email matches the contact. Links already established are retained when the contact email changes. Deleting a contact removes it from Contacts while keeping meetings; manual re-creation is supported. Contact edits do not change existing meeting invitations or workflow recipients. These records use the existing database without a new service.

Bookings automatically create contacts for their actual hosts, including each collective host, the assigned round-robin host and selected poll attendees. Names, email addresses and available phone answers are captured; existing contact details are preserved. Deleted contacts are not automatically recreated. Settings → Contacts settings (`/app/contact-settings`) can disable creation or exclude domains/email addresses. Use **Save changes**; exclusions accept commas or spaces and include subdomains. Existing contacts and their history remain available, and excluded addresses can still be added manually.

The first Contacts visit imports pre-feature booking history created from 2024 onward, respecting the saved opt-out, exclusions and deleted records. Later preference changes apply to new bookings; they do not rerun that historical import. Notetaker-based contact creation, external-form capture, email-interaction filters, merging existing records, multiple email/phone values and contact-specific booking/email actions remain to be implemented. See [the parity report](docs/PARITY_REPORT.md) for remaining comparisons and browser verification limits.

**Lists** contain contacts you choose. Select rows and use **Add to list**, choosing an existing list or creating one. Open a list and select rows to **Remove from list** after confirmation. **Manage lists and views** edits names or deletes a collection; deleting a list/view keeps its contacts and history. Lists and views belong only to the signed-in account. Conflicting edits require reloading; retries cannot reapply an earlier membership operation after a later removal.

**Contact automations → Add list automation** (`/app/contacts/automations`) or an event editor's **Contact automations** section configures automatic list membership separately for each event you host. Choose one or more existing lists or create a list. The **Enable automation** switch saves the selected lists immediately; **Save changes** saves destination edits without changing the enabled state. New lists persist immediately even if the automation is cancelled. A saved paused automation does nothing until enabled. Failures retain the draft; conflicting changes require a reviewed reload.

New bookings add the contact to every selected available list in the reservation transaction. Existing memberships are not duplicated. Settings changes, historical import and rescheduling do not add older bookings to lists; cancellation, pausing and deleting the automation retain existing members. A manual removal stays removed through a retry or reschedule, while a new independent booking can add that contact again. New-contact creation still follows Contacts settings; existing contacts can be organized even with automatic creation disabled. Deleted/excluded addresses are not automatically recreated.

For team events, each assigned host manages only their own contacts and lists; collective bookings apply each host's configuration, while round-robin bookings apply the chosen host's configuration. Assigned managed-event copies have their own configuration. Managed templates and polls are not configuration targets. Event duplication, source-created single-use links and managed assignment do not copy list automations. Deleted destination lists appear as unavailable; future bookings use any remaining valid destinations, and the automation can still be paused or deleted. Choose replacements before re-enabling. The limit of 100 destinations is a resource bound, not a paid tier. Automation settings and minimal booking/contact receipts use the existing database without an external service. Field/tag actions are described below; booking-answer mappings are described below. Opportunity creation is described below; original lifecycle/permission semantics remain open in the parity report.

**Contact automations → Add field automation** sets existing Text and Number fields or appends Tags for each new booking. Choose **+ Add field**, select a field and its value, and repeat for up to ten fields. **+ Create a new field** creates a Text, Number or Tags definition immediately, even if the automation is cancelled. The **Enable field automation** switch saves the draft immediately; **Save changes** saves value edits explicitly. Field and list actions have separate enable/pause/delete controls and can run together.

Text and Number replace previous values; Tags accumulate without duplicates. Existing single-tag values remain readable and become sets when edited or extended. Manual tag editing supports multiple selections; saved tag filters match membership, and CSV exports use JSON arrays for tag sets. Imports accept a single tag label or a JSON array of configured labels. Existing export snapshots are unchanged.

Field actions follow the same new-booking, host-ownership, retry, reschedule and contact-creation rules as list automations. Pausing/deleting retains applied contact values. Deleted fields, changed field types or removed tag options skip the affected action during future bookings; valid remaining field/list actions still run. The editor identifies broken targets and supports replacement, value repair or pausing. Saving uses the field definitions you reviewed; concurrent definition edits require reloading. Names can change without breaking the action. List and field updates share one booking receipt and transaction, so a storage failure rolls everything back. Date, Currency, Multi-select and Invitee question fields are not fixed-value automation targets; choose **Custom field source → Invitee question** for booking-question mappings.

**Views** update automatically as contacts match saved conditions. Use **Filter → + Add condition → Apply**, then **Save as view**, or create an empty view first. Changes to an existing view remain temporary until **Save view**. Search text is not saved. Views filter all contacts; a manual list's membership is not a saved-view condition. Filter errors from removed or incompatible custom fields show an explanation and can be repaired with the filter editor; they do not silently show all contacts.

Filters support standard details, source, creation dates, first/last past meetings, next meetings and custom fields. First/last/next meeting dates use noncancelled meetings for the contact's actual host. Date filters use the account's current timezone; ranges include both endpoints, before/after exclude the chosen date, and relative ranges include today. Empty values match **Is blank**, not **Is not within**. All/Any joins combine up to 20 conditions. New manual, CSV and booking contacts record their source; preexisting contacts remain Unknown rather than receiving guessed provenance. Exact original date/source semantics and UI still require browser comparison.

Use **Columns → + Create a custom field** to add up to ten text, number, currency, tag, date, multi-select or invitee-question fields. Each custom column has an **Edit custom field** menu; compatible edits retain values, while deletion removes that field's contact values without deleting contacts or meetings. Contact details includes **Edit custom field values** with explicit saving and conflict recovery. Decimal values keep their precision; dates use `YYYY-MM-DD`.

**Contact automations → Custom field source → Invitee question → + Map a question** selects one question for each event you host. **Enable** creates a new field named `Event title - Question label` and starts capturing new bookings. A suffix disambiguates an existing name. The Contacts field-creation entry point also creates and enables a mapping, using the name you enter. An event can have only one mapping per host, including paused mappings; existing fields cannot be reused as destinations.

Only new bookings update the mapped field. Setup, edits, historical contact import, booking retries and reschedules do not copy old answers or overwrite later manual edits. Nonblank future answers replace the prior value; unanswered questions preserve it. Pause, edit or delete the mapping from Contact automations. Changing the question creates a new destination and retains the previous field/values. Renaming a field leaves its booking question unchanged. Deleting the automation retains fields and values; explicitly deleting a custom field still removes its values. Missing questions or fields skip capture, and the automation can be paused/deleted or repaired with a new destination.

Question mappings, static fields and list assignment share the booking receipt and transaction. Existing legacy fields with a single mapping are adopted without rewriting values. Events with multiple legacy mappings are paused and marked for review, preserving all their fields and values. The ten-field resource limit still applies. Original mapping-edit and permission semantics, UI and browser behavior remain unverified under C14.

**+ Add contact → Import contacts from a file** accepts UTF-8 CSV with headings, Name and Email address. Map columns to standard or custom fields; exclude unwanted columns or create custom fields during mapping. Choose merge (fill empty fields), overwrite (replace mapped fields, including blanks) or skip for existing email addresses. Unmapped fields stay unchanged. Review the results before **Import contacts**. Changes to affected contacts or field definitions require a fresh review; uncertain retries confirm the same import without applying it twice. Repeated emails within a file are skipped after the first valid row. Invalid standard fields skip the row; invalid custom values leave that field unchanged and appear in the results. Download skipped rows with reasons or open imported contacts with field issues.

Imports support up to 1,000 contacts, 50 columns and 2 MB per file. Use `YYYY-MM-DD` dates, plain decimal numbers and configured tag labels; tag sets and multi-select values use a JSON array of option names inside the CSV cell. Creating a custom field saves it immediately, even if the import is later cancelled.

Select table rows to reveal **Export**. On All contacts with only text search, **Select all [count] contacts** includes every active contact in your account across pages and search filters. Inside a list/view or with advanced filters, **Select all [count] contacts in this selection** includes only current matches, across pages. This scope also applies to bulk list membership. All-selection membership is evaluated when confirmed; a changed saved list/view requires a refreshed selection. Exports include all standard/custom fields and create a private snapshot available for 24 hours, with an email link through the existing mail adapter. Without mail credentials, the download still works and the UI reports unavailable delivery; local demo mail stays in `.data/outbox/`. Links require signing into the owning account. Bulk membership and exports support up to 1,000 explicit IDs, or 20,000 contacts through Select all; exports additionally have a 25 MB bound. These are resource bounds, not paid tiers.

CSV exports and skipped-row downloads prefix spreadsheet-formula-like values with an apostrophe. This prevents formula execution but means those cells need review before reimport; currency exports contain the decimal value without a currency prefix. Export snapshots expire for access after 24 hours and are removed when accessed after expiry or when that owner creates another export. Import receipts retain IDs/results for retry safety; original CSV files are not stored. Both use the existing database (local PGlite in keyless development), with no new storage service.

Contact detail has **All**, **Notes** and **Meetings** timeline views. **Add note** accepts a title, body or both, with explicit **Save**. Notes are private to the contact's owner. The note menu edits or deletes it; editing moves it by its updated timestamp. Deletion removes the text and reminder from the record and cannot be undone. A minimal tombstone prevents delayed requests from recreating deleted notes; existing email summaries cannot be recalled.

Use **Add reminder** to choose a calendar date, **Complete** on the note to finish it, or edit the note to change/remove the date. Changing the date resets completion; text-only edits preserve it. **Reminders** (`/app/contacts/reminders`) lists pending due/overdue, upcoming or all reminders across your contacts. Notification links open the relevant note even when it is outside the first timeline page.

The existing `/api/cron/workflows` runner also processes contact reminders. On its first pass at or after 5 a.m. in the account timezone, it sends one daily summary of outstanding due/overdue reminders plus upcoming items. DST and account-timezone changes are respected. Overdue items repeat on following days until completed; a reminder added after that day's summary waits for the next day. The summary shows up to 100 due and ten upcoming entries, with a link to the full Reminders page. Without email credentials, reminders still work in the app and the UI reports unavailable email delivery. Local demo/development checks also record the summary in `.data/outbox/`. Run the existing cron route with a scheduler on your host for automatic delivery; no new service is provisioned by this feature.

Delivery attempts share a provider idempotency key and immutable payload. Failed/abandoned attempts can retry after 15 minutes, at most three times within a 23-hour window. Changed summary content or recipient cancels retries of the old snapshot. Notes edited or completed after dispatch begins cannot retract that email. Native browser behavior, original overdue/retry rules and Notetaker recap/multi-contact note creation remain unverified or missing; see the parity report.

## Calendar sync
- **Google**: its own OAuth client (`AUTH_GOOGLE_ID`), separate from Firebase sign-in. Add redirect URI `{APP_URL}/api/integrations/google/callback`; scopes `calendar.readonly` + `calendar.events`. Free/busy via the freeBusy API; bookings written with `sendUpdates=none` (we send our own invite) and a Meet link when the location is Google Meet.
- **Outlook / Microsoft 365**: Entra app (multi-tenant + personal accounts), redirect `{APP_URL}/api/integrations/microsoft/callback`, delegated `Calendars.ReadWrite offline_access User.Read`.
- **iCloud**: CalDAV at caldav.icloud.com with the Apple ID and an app-specific password.
- **Demo calendar**: keyless mock (dev or `DEMO_MODE=1`), busy 12-1pm ET on weekdays.
- Each user can connect several accounts, choose which calendars are checked for conflicts, and one calendar new bookings are added to. If a provider fails, its busy times are skipped and the connection is flagged.

## Opportunities

**Opportunities** opens a private board with five fixed stages: New lead, Intro call scheduled, Proposal sent, Completed and Check in later. **+ Add opportunity** saves a name, stage and contact, with optional amount, close date, source and notes. Search existing contacts or create one in the editor; a new contact is saved immediately even if you cancel the opportunity. Multiple opportunities can belong to one contact. Contact details links to that person's opportunities.

Drag a card into another stage, or use **Move to stage → Move** with a keyboard or touch device. Moves appear only after the server confirms them. Open a card to view/edit its details and stage history. Completed records stay on the board, and moves back to earlier stages remain in history. Search names or contact details, and page through each stage independently. There is no paid tier or opportunity-count cap; each stage displays 25 records per page.

Amounts preserve decimal precision (up to 15 whole digits and six decimal places); the currency selector labels the amount without charging or processing payments. Close dates use `YYYY-MM-DD`. Notes allow 10,000 characters and source text allows 500. Exact original currency/input behavior remains unverified. All records are private to their owner. Deleted contacts leave their opportunity records available and can be replaced through Edit.

Opportunity deletion permanently removes its details and stage history while preserving the contact and meetings. A minimal owner/ID/revision receipt confirms retries and prevents a lost creation request from recreating the deleted record. Conflicting edits/moves require a reviewed reload, and uncertain requests retain drafts. Stage history uses record revisions to preserve the sequence even when timestamps are identical. The UI displays history times in the account timezone.

**Opportunities → Automations → + Add new automation** creates a named rule for an event you host. Choose the destination stage and default opportunity name. **Insert variable** supports My name, Invitee full name, Invitee first name, Invitee last name and Meeting name. The event editor's **Contact automations → Create new opportunity** section and Contacts → Contact automations expose the same settings. Save/Enable starts the rule for future bookings; edit, pause and delete it independently. There is no count or subscription gate. The list searches automation names and paginates 25 rules at a time.

A new booking creates one opportunity per enabled rule, linked to the host's contact and booking details. Group invitees each create their own opportunity. Collective hosts apply their private rules, while round robin applies only the chosen host's rules. Existing contacts receive opportunities even when automatic contact creation is disabled; absent, excluded or previously deleted contacts follow Contacts settings. Historical import and rescheduling never create new opportunities. Booking retries cannot recreate an opportunity that was manually deleted.

**Booking origin → View booking details** opens the host's meeting detail with the invitee's answers. A same-host reschedule updates this link while preserving the opportunity's name, stage and manual edits. If round robin changes the host, the former host retains only their own cancelled booking link. Cancellation, pausing and deleting the automation retain existing opportunities. A deleted booking leaves its origin labels available without a broken link. Removed/reassigned source events remain visible for pausing, deletion or replacement from Opportunities → Automations.

Templates accept the five labeled variables as `{{my_name}}`, `{{invitee_full_name}}`, `{{invitee_first_name}}`, `{{invitee_last_name}}` and `{{meeting_name}}`. First name uses the first word; last name uses the remaining words. Expansion happens once, collapses whitespace and clips the result to 200 characters without splitting a surrogate pair. A blank result falls back to invitee name, meeting name, then Opportunity. Templates and automation names also allow 200 characters. These edge rules and the interaction with Contacts settings require original-browser comparison. Duplication, source-created single-use links and managed assignment do not copy automation rules.

Rules, opportunity links and shared retry receipts use the existing database. Opportunity creation commits with the reservation and other contact automations; a storage failure rolls back the whole transaction. No new service or payment handling is added. Original screenshots, native drag/drop and keyboard checks remain blocked by the browser environment; see O01/O02 in the parity report.

## Teams and automations
- Teams at `/team/<slug>`: collective (everyone must be free), round robin (spread evenly, or by priority then evenly), managed event types (copied into each member's account; locked fields follow the template). Invites go out by email and must be accepted by the invited address.
- Group event types: several invitees per time, up to the seat limit.
- Secret events: use **Make secret** in a personal event's menu, or the team event's administrator controls, to hide it from the public scheduling page. The direct booking link still works. **Make public** restores the listing; turning an event off separately disables new bookings. Assigned managed events can be hidden by their individual hosts; visibility is not a template lock.
- Booking date ranges: event editor → Availability supports rolling calendar days or weekdays, a fixed inclusive start/end date, or indefinite future availability. Use **Save changes**. Weekdays count Monday–Friday when extending the horizon; actual weekend/holiday availability still comes from the schedule. Fixed dates use the selected schedule's timezone (the creator's default schedule for team events). Existing events keep their rolling calendar-day count until edited; existing meetings are retained. Duplicates, source-created single-use links and managed assignments carry the range.
- **Location choices:** the event draft/editor offers Phone, In-person, Custom, Ask invitee and video meeting tiles. Phone can collect the invitee's number or provide the host's number after booking. In-person has an address and notes; Custom can show details before booking or reveal them afterward. Ask invitee requires a location answer. One-on-one and Collective events can offer several choices. Group events currently accept one common location, without individual invitee-supplied locations or phone numbers. These bounds still need original-browser comparison.
- **Video locations:** Zoom, Google Meet, Microsoft Teams, Webex and GoTo Meeting tiles accept a supplied HTTPS meeting link, revealed after booking. They do not connect an account or generate a meeting link. Automatic provider setup, per-host Round robin locations and the Collective conferencing organizer remain open work. New structured video choices do not silently create demo rooms.
- **Booked locations:** each reservation keeps the location selected when it was booked, including an empty location. Event edits affect new bookings; explicitly rescheduling a meeting (even at the same time) applies the new location. Confirmation, host details/CSV, calendar write-back, email/ICS and workflow location variables use the saved details. Existing conference links remain attached to their meeting. Poll bookings also retain their location, and group attendees share the session's saved location. The startup migration freezes the available location for legacy bookings once; earlier addresses that were never stored cannot be recovered. Existing text locations remain unchanged until replaced. Structured choices are copied by duplication, personal source-created single-use links and managed assignment; location locks protect both the label and configuration.
- Locked booking time zones: event editor → Booking page options → **Lock the timezone** fixes the zone invitees see and use to book, including direct links and rescheduling. Choose a named zone so daylight saving rules apply. This does not change the host's availability or move existing meetings. Unlocking restores the invitee timezone picker. Duplicates, single-use links from an event and managed assignments carry the setting.
- Start time increments: event editor → Booking page options controls spacing independently of meeting duration. New events default to 30-minute starts; presets and custom whole-minute intervals from 5 to 1440 are supported. Existing events retain their previous duration-based spacing during migration. Duplicates and managed assignments carry the setting, and administrators can lock it for assigned hosts.
- Account meeting limits: Settings → Scheduling → Advanced availability (`/app/availability/advanced`) automatically saves daily, weekly and monthly caps across all event types. Hosts manage their own caps; event owners/team admins can view them in the event editor. Event-specific limits remain separate.
- Workflows: email or SMS before or after a meeting, on booking, or on cancellation, with `{{variables}}`. Due messages go out from `/api/cron/workflows` (Vercel Cron every 5 min via `vercel.json`; set `CRON_SECRET`). SMS uses Twilio when `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_FROM` are set, otherwise it's logged.
- Routing forms at `/f/<id>`: questions plus first-match rules (is, is not, contains, is one of, ≥, ≤) that send people to an event type (prefilled), a URL, or a message.
- Demo mode has a second account (Sam, Chicago) so team features work with no keys.

## Conferencing, payments, embeds, branding, analytics
- **Legacy Zoom / Google Meet locations**: existing text locations named "Zoom" or "Google Meet" retain their provider behavior. Meet links come from Google Calendar write-back; Zoom uses a server-to-server OAuth app (`ZOOM_ACCOUNT_ID`, `ZOOM_CLIENT_ID`, `ZOOM_CLIENT_SECRET`, optional `ZOOM_USER`). With no keys, these legacy bookings get a labelled demo room at `/meet/<id>`. The new video tiles use the explicit supplied-link behavior described above.
- **Pending Google Meet links:** when a connected Google Calendar returns a pending or failed conference, the booking shows that state instead of substituting a demo room. Pending events are read through the existing workflow cron, at most twelve attempts spaced at least five minutes apart. The resolved link appears on invitee/host details and is shared by group attendees. Initial pending emails/ICS link to the booking page; they are not automatically resent when the link resolves. Provider failures, exhausted retries and expired meetings show that joining details are unavailable. This does not yet enable automatic conferencing in the new location picker.
- **Paid bookings (Stripe)**: set a price under "Payment and confirmation". The slot is held for 30 minutes while the invitee pays; emails, calendar events and workflows only fire once paid. Set `STRIPE_SECRET_KEY` (use a `sk_test_` key for test mode) and `STRIPE_WEBHOOK_SECRET`, and point a Stripe webhook at `/api/stripe/webhook` (`checkout.session.completed`, `checkout.session.expired`). Without keys a demo checkout at `/pay/<uid>` simulates payment. Rescheduling keeps the payment.
- **Redirect after booking**: optional URL per event type; gets `invitee_name`, `invitee_email`, `event_start`.
- **Embeds** (`/app/embed` builds the snippet; live demo at `/embed-demo.html`): `<script src="/embed.js">` then an inline `<div class="cid-inline" data-url=…>`, a popup widget (`CalendlyIsDead.initPopupWidget({url,text,color})`) or a popup text link (`data-cid-popup`). Frames auto-resize and post `{source:"calendlyisdead",type:"booked"}` to the parent page.
- **Branding** (`/app/branding`): brand color, logo, hide "Powered by". Embeds can override color with `?primary=RRGGBB`.
- **Analytics** (`/app/analytics`): new/cancelled/rescheduled/completed, page views and conversion per event type, revenue, popular-times heatmap.
- **Meeting polls** (`/app/polls`, public `/poll/<id>`) and **one-off links** (`/app/one-off`, single-use). Poll booking reviews meeting details and invitees, supports adding non-voters, and flags connected-calendar conflicts for confirmation. Failed calendar checks and overlapping app meetings block booking; buffer-only overlap is allowed. Votes are final with safe identical retries and a forty-participant limit. Hosts can choose whether public pages show vote counts and names; visibility defaults off, and voter emails stay private. Polls close when all offered times have passed.

## Email assistant (AI email-thread booker)
`/app/assistant`: paste a thread; it extracts people, length, days/parts of day, explicit times and time zone, intersects that with your real availability, and drafts a reply with one-click booking links (prefilled name/email). It never sends mail. Works keyless with a built-in parser; set `LLM_API_KEY` (+ optional `LLM_BASE_URL`, `LLM_MODEL`, any OpenAI-compatible API) to use an LLM. Inbound mail: POST `{to, from, subject, text}` to `/api/inbound/email` with `Authorization: Bearer $INBOUND_SECRET`, addressed to `<username>+<event-slug>@your-domain`; it returns the proposal and draft.

## Hosting under a sub-path

The app is served at `https://yourappisdead.com/calendlyisdead` via Next.js `basePath` (set in `next.config.mjs`, override with `NEXT_PUBLIC_BASE_PATH` at build time). Server-side absolute links use `APP_URL` (include the base path, e.g. `https://yourappisdead.com/calendlyisdead`); Auth.js runs at `${basePath}/api/auth`, so set `AUTH_URL=https://yourappisdead.com/calendlyisdead/api/auth`. Client code uses `BP`/`withBase` from `lib/basepath.ts` for `fetch`, plain `<a>` and `location.href`.

- Cron: `/calendlyisdead/api/cron/workflows` (vercel.json)
- OAuth callbacks: `${APP_URL}/api/auth/callback/google`, `${APP_URL}/api/integrations/{google,microsoft}/callback`
- Stripe webhook: `${APP_URL}/api/stripe/webhook`; inbound mail: `${APP_URL}/api/inbound/email`
- `npm run db:migrate` applies `lib/db/ddl.sql` to `DATABASE_URL` (the app also applies it on cold start).
- Without `RESEND_API_KEY`, mail is logged and skipped; booking and cancelling still succeed.
